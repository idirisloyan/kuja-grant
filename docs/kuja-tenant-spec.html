01Design principles

Five commitments define the Kuja tenant. The first three are the reason NGOs adopt us and the reason donors pay; the product must protect them in order.

01 · SELLING POINT

Barrier-free for NGOs

The system does the heavy lifting; the NGO answers plain, guided questions. Voice and photo are first-class input. One obvious next action, always.

02 · SELLING POINT

AI integrated, not a chatbot

AI lives inside each task — draft, check, score, structure, translate — with visible per-finding provenance. Money-gating stays deterministic.

03 · SELLING POINT

Works where NGOs work

Offline-first PWA, low-bandwidth, cheap Android phones. Writes queue and replay on reconnect.

04

Localized

French, Arabic (RTL), Spanish, Swahili, Somali + English. User language beats the tenant default.

05

Trustworthy

Deny-by-default, server-enforced; every governance action on a tamper-evident audit chain; every AI claim grounded and sourced.

NGOs never pay — monetization is structural on the donor/foundation side (licence + ERP upsell). That is why NGOs adopt: zero cost, minimum friction.

02Platform & integration

Kuja Grant is one of four products. The Kuja tenant integrates with Link (identity + entitlements), Trust (the due-diligence engine), and Build (ERP financials). Every organization carries a shared identity key (kuja_partner_id = Odoo res.partner id) that joins them.

03Personas

Four roles (User.role): ngo, donor, reviewer, admin. Authorization is server-side and deny-by-default; donor publish/award is additionally licence-gated (off by default today).

NGO

Applicant

Discover grants; apply AI-guided & offline; submit; respond to revision/doc requests; report by voice or photo. Never licence-gated, never pays.

DONOR / FOUNDATION

Grant-maker

Create & publish grants; set criteria; assign reviewers; award; oversee compliance & reporting; map ERP financials.

REVIEWER

Assessor

Score assigned applications against the weighted rubric; disclose COI; private notes never shown to the NGO.

ADMIN

Platform operator

Provisioning, licensing, compliance oversight, AI-quality + cost telemetry, audit-chain integrity.

04End-to-end lifecycle

One grant, four personas, seven stages — AI embedded at each step, offline-safe on the NGO's side, deterministic where money is gated.

05AI integration — not a chatbot

A heavily-wired system today, not scaffolding: a real Anthropic path with a consistent budget-gate → telemetry → provenance → replay plumbing behind every surface. Intelligence lives inside the tasks. Crucially, the surfaces that gate money or must be explainable are deliberately deterministic.

Grounding & guardrails

  • Per-claim provenance — AIProvenance stores basis / source / confidence for each AI finding; extracted items are tagged ai_extracted · ai_edited · manual so a human always sees what came from the model.
  • Server-side output validation — forced tool-use against a JSON schema; a deterministic fallback dict when the shape is missing; 8 flagship surfaces contract-checked against fixtures.
  • Replay + false-confidence loop — full calls persisted for admin replay; the UI records when an AI output was accepted verbatim then corrected, rolled up as false_confidence_rate per language.
  • Cost & degradation — a hard per-org budget inside the call path; missing key / over-budget / timeout / malformed all shed to deterministic templates; a service-status banner keeps the workflow honest. There is always a non-AI path.

Design item: there is no single registry of mutating AI actions yet — the equivalents are a read-only query-tool registry, provenance, and extraction tagging. A closed action-catalogue for any AI-proposed mutation is recommended hardening (Roadmap, Phase 5).

06Financials — with our ERP and without it

The tenant must serve both kinds of donor: those who buy Kuja Build and those who don't. A single financial_source = erp | manual abstraction returns one normalized shape from GET /api/grants/<id>/financials, so compliance and reporting read the same thing either way.

07Offline & localization

Offline-first / low-bandwidth

A custom service worker (network-first navigations with a cached shell, cache-first static, stale-while-revalidate reads) plus an IndexedDB outbox that queues writes and replays on reconnect. Static export removes SSR round-trips. to build extend the outbox from 2 surfaces to the NGO's critical writes — application submit and report create/submit.

Localization

Six full locale catalogues with a target→English→key fallback and Arabic RTL; user language beats the tenant default. Coverage: Arabic ~99.5%, Somali/Swahili ~93.7%, Spanish ~93.2%, French ~91.5%. to build finish fr/es/sw/so, fix three surfaces that bypass t(), and localize integration-seam error bodies; Whisper server transcription unlocks Somali voice (unsupported in browser speech).

09Roadmap

PHASE 0 · THIS CYCLE

Kuja-scoped, inert-safe

Trust tenant-guard + docstring fix; licensing upgrade prompt; Build operator mapping UI; donor/admin financials panel.

PHASE 1

Identity & entitlements

Inbound Link→Grant billing webhook; OIDC SSO + res.partner linking; licence provisioning; flip enforcement.

PHASE 2

Trust as one engine

Identity backfill → shadow → remote → retire the local DD fork.

PHASE 3

Build ERP live

Fill the finance call to the dev-team contract; wire live financials into the report bundle + compliance.

PHASE 4

Barrier-free depth

Offline outbox on submit/report; finish fr/es/sw/so + the 3 hardcoded surfaces; Whisper for Somali.

PHASE 5

AI depth

More embedded surfaces + provenance coverage; a closed mutating-action catalogue; accept/edit/dismiss quality loop.

10What we need

  • Link — OIDC IdP details + the billing→entitlement webhook contract (events, payload, signing) + the Link test env; which donors are already Link members (SSO onboarding candidates).
  • Trust — the org identity backfill (map res.partner ↔ grant org).
  • Build — the finance API contract: endpoint, read-only service account, one sample payload (sign/currency/FX), and the grant↔analytic-account (build_ref) mapping + freshness model.
  • Licensing — which donor orgs to license first + the go-live date to flip enforcement.
  • Localization — native reviewers for fr/es/sw/so sign-off.
