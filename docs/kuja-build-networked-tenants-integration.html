Kuja Build ↔ Networked Tenants

Financial integration for the non-Kuja tenants — Proximate & Saxansaxo. A tenant pulls real, booked financials for a single donor grant from the operator's Kuja Build ERP, scoped so the donor sees only their grant. No Link, no shared identity, no Trust engine.

Framing

01  Why this is a separate spec

The Kuja-tenant Build seam assumes a shared Link (Odoo) identity — the donor logs in through Link and the grant↔Build link is derived from the shared res.partner. Proximate and Saxansaxo don't use Link. They authenticate their own users, do community-based trust, and run under their own network. So the Build connection needs a mechanism that doesn't depend on Odoo SSO — different enough to keep in its own spec, so the two tenants never get conflated.

Architecture

02  One binding, one feed, existing scope

Bind one grant to one Build account, feed it over a service credential, show it through the donor scope you already enforce. Three layers — only the middle one is tenant-specific.

Tenant-agnostic (shared)
  • One BuildClient (service credential)
  • Normalise to budget_lines / actuals / disbursements
  • Same shape the Kuja seam uses
Tenant-specific
  • Operator sets build_ref per grant
  • Human auth = tenant's own login
  • Surfaces in the tenant's scoped donor reporting

The crux

03  Multi-tenant isolation

Adeso's Build holds many grants from the same donor. QCF must see only the account funding the Proximate grant — never Adeso's other QCF grants. Isolation is a composition of three controls; we want all three.

The three controls
  1. Single-ref binding — the grant stores one build_ref, resolved server-side; no enumeration.
  2. Donor scope — the donor account is already scoped to its grants; the financials inherit that scope.
  3. Source-side scoping — Build exposes only the one account (record rules / per-grant token).
Isolation by record

The feed is keyed off the grant's stored build_ref, resolved from a grant the viewer is already authorised to see — a request never supplies an analytic-account id.

Load-bearing risk

If the Build service credential can read all of Adeso's finance data, isolation rests entirely on control 1 (the grant-app side). Source-side scoping (control 3) is what makes "QCF only sees the Proximate grant" a structural guarantee rather than a filter that could be forgotten. This is the single most important thing to settle with the dev team.

Mechanism

04  The connection, per grant

Shipped 14 Aug 2026 · Phases 0–1, inert on prod

The tenant-agnostic scaffold is built and deployed, dormant until a Build client is configured — prod behaviour is unchanged. Live now: Grant.financial_source (erp | manual, default manual) + build_ref + financial_synced_at; build_client.py (env KUJA_BUILD_BASE_URL / KUJA_BUILD_SERVICE_TOKEN; keyed only by the ref); build_engine.py (the erp | manual selector); and the endpoints POST /api/grants/<id>/financial-source (operator, admin-gated + audited), GET /api/grants/<id>/financials (donor-scoped), GET /api/admin/build/status. The only thing left is the concrete finance-API call — which needs the sample payload below.

  1. Operator maps the grant. Sets financial_source = 'erp' and build_ref = <analytic account id> on the donor grant — one audited action.
  2. Backend pulls on demand. The grant backend calls BuildClient.get_financials(build_ref) with the service credential, keyed off the grant's stored ref — never a request value.
  3. Normalise + cache. Build's response is normalised to the shared shape and cached with last_synced_at; the donor sees booked actuals vs budget.
  4. Fallback is seamless. With financial_source = 'manual' (or Build unreachable) the same surface renders uploaded reports — compliance is identical either way.
Proof

05  Reference use case — QCF → Proximate

A real, self-contained proof on actual Adeso financial data already loaded in the Build test env.

Setup & map
  • Proximate is funded by QCF; Adeso holds several QCF grants
  • The specific Proximate-funding grant is uploaded to the tenant; QCF has a scoped donor account
  • Operator maps that grant's build_ref to the QCF analytic account
Acceptance

positive QCF sees real budget vs booked actuals + disbursements for its Proximate grant.

negative QCF cannot see Adeso's other QCF grants — no mapping, no scope, no source access.

parity Saxansaxo is the same shape — proving one proves the pattern.

Why this approach

06  Benefits

  • One feed, every tenant. Same client + abstraction for Kuja, Proximate, Saxansaxo — no per-tenant financial code to drift.
  • Decoupled from identity. Never touches Link/SSO — works for tenants that authenticate their own way.
  • Isolation by construction. Per-grant build_ref makes "donor sees only their grant" structural, not a filter to remember.
  • Compliance with or without the ERP. erp | manual — a grant without Build still reports via uploads on the same surface.
  • Real numbers, less reconciliation. Donors see actuals booked in the accounting system, not re-keyed figures.
  • Reuses hardened plumbing. Rides existing donor scoping + hash-chained audit; no new access-control surface.
  • Incremental & reversible. Flag-gated inert rollout — ship dormant, map one grant, prove, expand.

Before we build

08  What we need from the dev team

A · Build finance API access (test env first)

  1. Test-env base URL + which API: Odoo external API (XML-RPC / JSON-RPC) or a custom REST endpoint.
  2. A dedicated, read-only service account + credentials for the grant backend (not a human login).
  3. Rate limits / SLA on the finance API, and whether prod Build exposes the same API shape.

B · The mapping keys (for the QCF → Proximate test)

  1. The analytic account / project id in Build for the QCF grant that funds Proximate (the build_ref).
  2. A second, unrelated QCF analytic-account id, for the negative isolation test.
  3. The Build grant model: is there a grant.grant object or only analytic accounts/projects? One account = one donor grant, or many:1?

C · The data contract (one sample per object)

  1. A sample payload for that account: budget lines, booked actuals (journal / analytic lines), disbursements/payments — with field names + types.
  2. Semantics: amount sign conventions, currency (grant vs company — QAR/USD) and where FX conversion happens, date fields, how categories are identified.
  3. How Adeso's Build-booked disbursements relate to the tenant's own recorded disbursements — same events to reconcile, or complementary?

D · Isolation at the source (the security ask)

  1. Can the service account be scoped per analytic account (Odoo record rules), reading only the mapped account?
  2. If not — can Build issue a per-grant grant.dashboard.share-style token (public id + secret, hash-only) scoped to one account, that the backend calls instead of a broad credential?

E · Freshness & operations

  1. Feed model: pull-on-view, scheduled sync, or webhook-on-posting? Expected latency? If webhook: event catalogue, payload, signing.
  2. Confirm the test env holds the real Adeso financial data for this grant, and the entitlement model — ERP/real-time gated per donor or per grant, and who provisions it.
What we'll do in parallel

Phases 0–1 (the financial_source/build_ref mapping + the BuildClient scaffolding) can be built now and left inert behind a flag. The moment items A–B land, the QCF → Proximate test is just: point the client at the test env, set the one build_ref, and run the positive + negative checks.
