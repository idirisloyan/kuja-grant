Overview

01  Scope & the four products

This spec defines three integration seams around the main Kuja tenant. It does not merge codebases — each product keeps its own stack. It connects them through a shared identity and a shared organisation record so a member experiences one platform.

In scope
  • Single sign-on from Kuja Link into Grant
  • Donor licensing + the NGOs-free guarantee
  • Grant delegating due diligence to Trust
  • Build ERP financials feeding Grant's compliance & reporting
  • One shared organisation identity across all four
Non-goals (for now)
  • Merging the Grant and Trust databases
  • Rebuilding grant dashboards or compliance inside Odoo
  • Moving billing out of Odoo
  • Other tenants (NEAR / Proximate / Saxansaxo) — Kuja tenant first

Architecture

02  Link is the backbone; Grant is the hub

Kuja Link (Odoo) owns identity and membership. Grant, Trust, and Build all key off one shared organisation record. A member logs in once at kuja.org; a launcher opens Grant; Grant leans on Trust for due diligence and on Build for live financials. Same person, same org, everywhere.

Foundation

03  Identity & entitlements

Everything hangs on two ideas: one organisation identity shared across products, and entitlements that decide what a donor org may do. Both are small, explicit, and live where they're cheapest to reason about.

Shared organisation identity

The Odoo res.partner id is the join key. It is stamped onto the Grant app's Organization, the Trust org, and the Build company — so "one member, one org, four products" is true by construction.

Entitlements (per donor org)

Two independent flags, both read by Grant. Neither ever touches NGO capabilities.

grant_licensed # may publish & award grants
has_kuja_build # finance feed available (real-time)

Source of record: Grant app admin. Billing stays in Odoo; the flags can later reconcile to it.

The load-bearing rule

Entitlements gate donor powers only (publishing grants, live financials). Every NGO capability — applying, the capacity assessment, the Trust Passport, uploading reports — sits outside every entitlement check. NGOs are free by construction, not by policy.

Seam 1 · Link ↔ Grant

04  Single sign-on & the licensed module

Odoo acts as an OpenID Connect provider. A "Grants" tile in the Kuja Link portal launches the grant app with a signed token — no second password.

  1. Member is on kuja.org, already signed in. A Grants tile appears for every member.
  2. Click launches SSO. Odoo redirects to Grant with an OIDC token: identity, email, Kuja Link org (partner_id), role, and the two entitlement claims.
  3. Grant provisions or links. First time in, Grant creates (or matches by partner_id/email) an Organization + User in the Kuja tenant. No signup form.
  4. Entitlement check — inside Grant. Licensed donor → full powers (open a programme, publish a call, award). Unlicensed → an upgrade path. NGO → full free access. Decided by Grant's own flags.
  5. They land in the module as the right persona, scoped to their org, one identity shared back to Link.

Seam 2 · Grant ↔ Trust

05  One due-diligence engine

The grant app already carries a fork of the Trust engine — same two-pillar model, identical weights, same checks, its own passport + credential — that has drifted behind. "Reuse Trust" means Grant calls Trust and we retire the fork, which also erases three real bugs it carries.

Shipped 14 Aug 2026 · Phase 3 code, live in prod

Trust now exposes authenticated service endpoints (/api/service/trust-profile, /api/service/screening/run; bearer KUJA_TRUST_SERVICE_TOKEN, constant-time compare). Grant delegates through an engine selector KUJA_TRUST_ENGINE = local | shadow | remote, verified end-to-end from inside the grant container. Left on local, so prod behaviour is unchanged.

Grant always calls Trust's live prod URL — never a pinned copy — so every new Trust deploy is picked up automatically; the only stable contract is the /api/service/* response shape. The shadow→remote cutover is held until the identity backfill lands (§09), so parity is measured on real orgs, not just the seeded demo org.

Grant delegates to Trust
  • Run screening (sanctions / PEP / SAM / adverse media)
  • Compute the two-pillar trust score
  • Issue & verify the Capacity Passport + credential
  • Evaluate a donor's funder policy against an org
Grant keeps for itself
  • The mandatory capacity gate on membership
  • The per-application diligence Q&A room
  • Reviewer & award flow (reading Trust)
  • Grant lifecycle, reporting, notifications
Three bugs in the grant fork we retire on the way out

bug  Every issued Verifiable Credential serialises its pillar scores as null.

bug  The "re-assess before disbursement" freshness gate is written and displayed but never enforced.

bug  A never-screened org and a sanctioned org both score 0 on diligence. Trust already fixes this (no-data ≠ fail).

Seam 3 · Build ↔ Grant

06  ERP financials — the upsell

Kuja Build (Odoo accounting) is sold as an upsell. When a donor buys the ERP for themselves and their NGO, the grant's financial actuals flow into Grant's compliance & reporting in real time. When they don't, they upload reports — and compliance works exactly the same. The trick is to make Grant's compliance read one normalised shape, whatever the source.

Two channels, kept distinct

A · Authenticated data feed core

Build to Grant, system-to-system, over a service credential (OAuth client / API key on the shared org id). Structured financial data — budget, actuals, disbursements — feeds the financial-source pipeline. This is the upsell's real value.

B · Public dashboard share complement

Your dev team's grant.dashboard.share spec: a tokenised, no-login link so a donor or auditor can view a read-only dashboard. Keep it — for human viewers. Don't run channel A over its auth="none" token.

System of record

Grant owns the grant, budgets, compliance, and reporting. Build owns the ledger and actuals. Odoo's grant.grant is a finance projection keyed to the Grant-app grant — not a second grant, and not a place to rebuild dashboards the Grant app already has.

Cross-cutting

07  Security model

  • Two credential classes. Humans authenticate via Kuja Link SSO. Systems talk to each other via scoped service credentials. Public magic-link tokens are for external humans only — never a system-to-system channel.
  • Isolation by record, not by URL. Every shared or cross-system lookup resolves through a validated record (share, membership, org link) and never trusts an id supplied in a URL — the pattern the dashboard-share spec already follows.
  • One audit spine. Grant and Trust both hash-chain their audit logs; the Build feed and every share create/revoke append to it, so "who saw what, when" is answerable end-to-end.
  • Least data. Explicit serializers (allowlist, per audience) decide what leaves each system. Store token hashes, never raw tokens. Financial links carry a TTL.

Before we build

09  Open questions & what we need

The Grant↔Trust seam is built and deployed; the one remaining input is the identity mapping (below). The other unknowns are on the two Odoo environments — Link and Build. Your team has stood up test environments for both; with access plus one sample payload we can start immediately.

Immediate ask · unblocks the shipped Trust path

One item stands between the deployed Trust integration and a live remote cutover: the org identity mapping — for each Grant Organization, its Odoo res.partner id (a CSV of grant org id / email → partner_id, or the Odoo member export). We backfill Organization.kuja_partner_id (Grant) and organizations.external_ref (Trust) from it, then flip KUJA_TRUST_ENGINE shadow → remote and retire the fork. Nothing else is blocked on it.

Open questions
  1. Is the shared dashboard Odoo's own finance view, or the Grant app's dashboard fed by Build data?
  2. Does Build hold a real grant model, or only the finance projection? How does it map to a Grant-app grant?
  3. What financial objects does Build expose per grant — budgets, analytic actuals, journal lines, disbursements — and at what granularity?
  4. Is the feed pull-on-view, scheduled sync, or webhook-on-posting? What freshness do donors expect?
  5. In Build, is each donor + NGO a separate company, or one DB with record rules?
